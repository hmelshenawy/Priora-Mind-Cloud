# T039 --- Event Memory Extraction

## Phase

Event Memory

## Goal

Automatically extract structured Event Memory candidates from user
conversation using the LLM.

T037 added the Event data model and migration. T038 added Event
persistence. T039 adds the extraction layer that converts
natural-language user input into structured Event data.

## Core Rule

Conversation history is context only. Only information introduced or
explicitly confirmed by the current user message may produce a new
Event.

History may be used to resolve references such as "they", "the company",
"that interview", temporal expressions, and previously mentioned
entities. It must not cause old Events from conversation history to be
extracted again.

## Scope

### 1. Event Extraction Schema

Define a structured LLM response model supporting zero, one, or multiple
Event candidates.

Each Event contains: - `summary` - `occurredAt` (optional) -
`entities` - `participants` - `concepts` - `salience`

Embedding is not generated by the LLM.

Example:

``` json
{
  "events": [
    {
      "summary": "User was invited by Microsoft for a second technical interview for an AI Engineer position",
      "occurredAt": "2026-10-07T00:00:00Z",
      "entities": ["Microsoft", "AI Engineer"],
      "participants": [
        {"entity": "user", "role": "candidate"},
        {"entity": "Microsoft", "role": "employer"}
      ],
      "concepts": ["career", "job interview", "AI Engineer"],
      "salience": 0.85
    }
  ]
}
```

If no meaningful Event is introduced:

``` json
{"events": []}
```

### 2. Event Extraction Prompt

Create explicit extraction instructions distinguishing context from the
current extraction target.

``` text
You extract Event Memories.

CONVERSATION_HISTORY is context only.
Do not extract events from conversation history.

Extract only events introduced or explicitly confirmed by CURRENT_USER_MESSAGE.

Use CONVERSATION_HISTORY only to:
- resolve references
- resolve entities
- understand temporal expressions
- understand the meaning of the current message
```

Input should clearly separate:

``` text
<CONVERSATION_HISTORY>
...
</CONVERSATION_HISTORY>

<CURRENT_USER_MESSAGE>
...
</CURRENT_USER_MESSAGE>
```

### 3. Event Detection

Do not treat every action or sentence as persistent Event Memory.
Extract events useful later for understanding the user's life, work,
goals, relationships, projects, decisions, progress, or important
experiences.

Trivial actions should normally not become Event Memories.

`I bought milk.` normally returns `{"events":[]}`.

`Microsoft invited me for a second technical interview.` produces an
Event candidate.

### 4. Salience

The extractor assigns a `salience` score from `0` to `1`, representing
likely usefulness for future understanding and assistance.

Do not add redundant fields such as `should_store` or `reason`.

Storage threshold logic is separate from extraction. Initial threshold
tuning will be handled separately based on observed behavior.

### 5. Multiple Events

Support multiple Events when the current user message genuinely
introduces multiple distinct events. Events should remain atomic enough
to be independently stored and retrieved.

### 6. No-Event Behavior

The extractor must return a valid structured response when no Event
exists. Never force an Event from every user message.

## Out of Scope

-   Event persistence changes
-   Event semantic retrieval
-   Event deduplication
-   Dynamic Episode reconstruction
-   Episode tables or `episodeId`
-   Concept normalization or Concept tables
-   Event relationship discovery
-   Unified semantic Memory + Event extraction
-   Changes to existing semantic Memory extraction
-   Final salience storage threshold tuning
-   Frontend Event Memory UI

## Acceptance Criteria

-   Structured Event extraction schema exists.
-   LLM can return zero, one, or multiple Event candidates.
-   Events contain summary, optional time, entities, participants,
    concepts, and salience.
-   Salience is constrained to `0..1`.
-   Conversation history can be supplied as context.
-   History is explicitly context-only.
-   Only the current user message can introduce new Events.
-   Context can resolve references in the current message.
-   Old Events are not intentionally re-extracted from history.
-   Trivial messages can return an empty Event list.
-   Embeddings are not generated by the LLM.
-   Existing Event persistence remains unchanged.
-   No Episode persistence is introduced.
