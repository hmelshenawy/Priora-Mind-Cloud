# RAG Service logging audit

Date: 2026-11-07. Static, read-only application review; recommendations only.

## Findings

Live ingestion prints every chunk, and `/v1/embed` prints all embedding inputs. Evaluation scripts additionally print questions, reference answers, and retrieved text. Remove these content dumps first. Existing useful counts are unstructured; request completion, elapsed time, failure stage, and correlation are absent. No explicit vector or credential logging was found in application source, but dependency/access logs and exception output need separate scrutiny.

Scope: all Python source and logging/launch configuration under `rag-service/`, including CLI and evaluation scripts; Agent and backend callers inspected for correlation. Line numbers refer to this checkout. Generated bytecode, installed dependencies, runtime output, and secret environment files were not audited. No services or evaluation scripts were run.

## Minimal proposed event contract

Use existing Python `logging`, a small `LoggerAdapter`, `ContextVar`, `uuid4`, and `perf_counter`; no dependencies or new framework. Match the Agent's single-line `request_id=<id> event.name key=value` convention. Use `service=rag`, fixed event names, bounded scalar fields and integer `duration_ms`. Default application INFO; opt-in DEBUG for stage diagnosis. Do not add per-page, per-chunk, per-vector, or per-batch logs.

| Event / level | Placement | Safe fields beyond request ID and service |
| --- | --- | --- |
| `request.started` / DEBUG | Request boundary before parsing/auth dependencies (`main.py:14,32-34,67-69,81-83`) | `method`, route template, `operation=ingest|search|embed` |
| `storage.download.completed` / DEBUG | `storage.py:15-18` | `byte_count`, `duration_ms` |
| `document.extract.completed` / DEBUG | `pdfExtractor.py:8-19` | `page_count`, `duration_ms` |
| `chunking.completed` / DEBUG | `main.py:47-49` or chunker return, one owner only | `chunk_count`, configured size/overlap, `duration_ms` |
| `embedding.model.loaded` / INFO | `embedding.py:5-6` | Allowlisted model name, `duration_ms`; startup has `request_id=-` |
| `embedding.completed` / DEBUG | `embedding.py:9-15`, shared by all three endpoints | `input_count`, `vector_count`, actual `dimension`, allowlisted model name, `duration_ms` |
| `qdrant.collection.created` / INFO; `qdrant.collection.checked` / DEBUG | `qdrant_client.py:46-93` | Safe configured collection alias, expected dimension, `duration_ms` |
| `qdrant.upsert.completed` / DEBUG | `qdrant_client.py:29-43`, after all batches return | `point_count`, `batch_count`, `duration_ms`; `wait=True` already exists, no behavior change |
| `qdrant.search.completed` / DEBUG | `qdrant_client.py:150-167` | `top_k`, `result_count`, `duration_ms`; no scores, result IDs, filter values or payloads |
| `request.finished` / INFO on success | Whole request boundary after response completion | `operation`, `method`, route template, actual `status_code`, `outcome=completed`, total `duration_ms`; ingest: page/chunk/indexed counts; search: top_k/result count; embed: input/vector count/dimension |
| `request.finished` / WARNING on expected rejection; ERROR on failure | Same boundary, exactly once | `outcome=rejected|failed`, `stage`, stable `error_code`, safe `error_type`, actual status when available, elapsed duration; failed upsert may include successfully completed point/batch counts |

One INFO request summary normally suffices; DEBUG reveals aggregate stage durations. No separate ingest/search completion event is needed. Do not claim indexing completed before all upserts return. Do not log `EMBEDDING_BATCH_SIZE` as an effective encode setting: it is imported but not passed to `encode` (`embedding.py:1,10-12`).

Measure total elapsed time using a monotonic clock, including authentication, parsing, dependency work, and response sending. Track a bounded stage such as `parse`, `auth`, `download`, `extract`, `chunk`, `embed`, `collection`, `map`, `upsert`, or `search`. Preserve exceptions, HTTP status, responses, cancellation, and existing control flow. If the request is cancelled, record `outcome=cancelled` at DEBUG and re-raise; do not invent a returned HTTP status. Startup failures need one ERROR `service.start.failed` with stage/error code because they occur outside the request boundary (`main.py:15-18`).

Level rules: INFO for successful request summaries and actual lifecycle transitions; DEBUG for aggregate stage detail and optional starts; WARNING for expected auth/client rejection or an actually recovered/degraded operation; ERROR for an unrecovered dependency/internal failure. Zero search hits alone are not a warning. Do not relabel current unhandled parse errors as 4xx or introduce retries/validation in a logging-only change. Log a failure once at the owning request boundary, rather than in every layer; preserve enough safe stage metadata to diagnose it. Successful health requests should be DEBUG or omitted, while health failures remain visible.

## Sensitive-data policy

- Confirmed exposure: chunk text (`chunker.py:41,99`), embedding inputs (`main.py:85`), file bytes (`storage.py:17`), evaluation questions/reference answers/retrieved text (`evals/runner.py:94,97,108`; `evals/test.py:53`). Remove rather than demote to DEBUG.
- Potential exposure: raw exception strings (`evals/runner.py:72,76,128`) and dependency/server output may contain URLs, storage paths, provider response bodies or input fragments. Prefer stable error codes and exception class names. Avoid automatic `logger.exception`, `exc_info=True`, exception `repr`, or stack-local dumps without a demonstrated sanitization policy; ordinary traceback rendering can include exception messages. Check Uvicorn's separate error path so it does not bypass this policy.
- Never log queries, document names, storage keys, extracted text, embedding inputs/values, request/response bodies, Qdrant point objects, headers, credentials, signed URLs or environment/config dumps. Qdrant payloads contain text, filename and tenant metadata (`qdrant_client.py:133-146`); search returns payloads (`:156`) and `/v1/embed` returns vectors (`main.py:89-90`). These are returned application data, not existing log calls; do not add response logging.
- Request IDs are sufficient for routine correlation. Omit raw `mindSpaceId` and `source_id` by default; they identify tenant/document records. If document-level lookup is later required, explicitly approve a bounded opaque identifier. Never hash document/query content as a substitute for omission. Treat collection/model names as configured allowlisted values, not arbitrary strings or local paths.

## Agent-compatible request correlation

The Agent already uses `ContextVar("agent_request_id", default="-")` and a `RequestLogger` prefix (`agent-service/src/agentcore/memory/memory.py:17-25`). It creates a UUID hex ID inside the chat stream, measures duration, and resets the token in `finally` (`agent-service/src/agentcore/main.py:61-88`). Its configuration is stdlib key/value text, not JSON (`:18-26`). Reuse the convention locally in RAG rather than importing Agent modules or introducing shared infrastructure.

Cross-service propagation does **not** exist in the inspected callers: Agent search headers (`agent-service/src/agentcore/tools/knowledge.py:19-30`), both embedding callers (`agent-service/src/agentcore/memory/memory.py:123-132,310-320`), and backend ingestion (`backend/src/documents/rag.service.ts:16-28`) send no request ID.

Recommended later implementation:

1. At RAG ingress, accept a bounded safe `X-Request-ID` (for example 1-64 ASCII letters/digits/underscore/hyphen, compatible with Agent UUID hex); otherwise generate `uuid4().hex`. Never echo/log an invalid header verbatim or reject the request just for this logging metadata.
2. Set a RAG-local ContextVar before dependencies execute; retain it through the final request log and reset its token in `finally`. Ensure auth failures, malformed bodies, concurrent requests and cancellation retain the correct context. Context propagation must be verified at any thread/callback boundary; a global mutable request ID is unsafe.
3. Agent callers should forward their existing request ID in `X-Request-ID`. Backend ingestion needs its own request-scoped ID forwarded to RAG. These are future caller changes, outside this audit; RAG-generated IDs alone cannot establish cross-service tracing.
4. Optionally return the validated/generated ID in `X-Request-ID` for support correlation, with no body/status changes. If several RAG calls share one Agent ID, a separate local `operation_id` can disambiguate concurrent calls if needed; do not add it until necessary. Correlation IDs are diagnostic metadata, never authorization.

## Review and validation

Implementation priority: remove content dumps; add request correlation/completion and safe failure ownership; replace aggregate prints with DEBUG stage events; align dependency/access output and evaluation summaries. All recommendations preserve current RAG behavior and use only existing/standard-library facilities.

This audit used source inventory, logging/output searches, caller inspection and line-reference review. No runtime safety or logging coverage claim is made. Before a later implementation is accepted, capture logs for ingest/search/embed success, zero hits, auth rejection, malformed input, dependency failure, partial upsert, concurrent IDs, and cancellation; assert no content/credentials appear and exactly one terminal request record is emitted with correct durations/IDs. Verify normal responses and errors remain unchanged. No application code, dependencies or deployment configuration were modified; no commit or push performed.
